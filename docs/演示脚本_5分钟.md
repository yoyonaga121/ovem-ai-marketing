# OVEM v3.0 Agent 工作台 · 5 分钟演示脚本

> 用途：面试现场 / 录屏演示，按 5 步走完「成果层 → 执行层 → 失败分支 → 人工闸门 → 评测回归」。
> 演示口径：本地 `file://` 打开，不依赖网络；所有数字来自 IndexedDB `ovem-os-v3` 实际运行记录。
> 目标时长：**5:18（≤ 5:30）**；纯操作约 40 秒，其余为讲解与停顿。

## 0. 开场（20 秒）

打开 `OVEM站点_v2.0/index.html`，停在 P0 首屏。

> “这不是一份静态作品集，而是一个可运行的 AI 营销系统。左边 17 页是成果层，右上角进入 Agent 工作台；成果页上的每一条血缘、每一张产物卡，都来自同一次真实 run。”

## 1. 成果层：17 页都有出处（45 秒）

**操作**：在 P0 顶部血缘条停留 → 滚到 P4 右栏 → 打开 P7 渠道状态条。

**讲解点**：
- P0：`17/17` 页有血缘条；最近一次生产 run（演示库当前 `R-0059`；S4 冻结快照 `R-0034`），7/7 步、9 次调用、¥0.1168、3 件产物、850ms。
- P4：三张产物卡（官网 16:9 / 移动 9:16 / 社媒 3:4）的 `runId` 与 P0 同一 run（当前 `R-0059`），不是手工贴图。
- P7：三个渠道的“待审”状态由 `artifacts.status` 派生，run 换状态，页面跟着换。

**收句**：
> “成果层只读运行态，不复制第二份内容；所以它既能当作品集，也能当系统证据。”

## 2. 工作台 A：一条 Brief 跑成可审物料（70 秒）

**操作**：进入 `workbench.html`，选预设 A「P01 · W3 旗舰物料包」，点「运行 Mission」。

**讲解点**：
- Mission 只有一个 Brief：产品 P01、三渠道、预算 ¥200。
- Plan 是 7 个步骤，Trace 是 30 条事件；7 步不等于 9 次调用，`channel.spec` 和 `artifact.land` 是显式工具。
- 终态 `review`：物料已生成、等待人审；成本 `¥0.1168`，来自 `tokens/1000 × 0.004 + images × 0.03`，不是估算。
- Artifacts 三张卡带比例、QA 86、状态待审；点任一卡可看到它属于本次 run。

**收句**：
> “这一屏回答的是：AI 到底做了什么、花了多少、产物在哪、为什么停在这里。”

## 3. 工作台 B：失败不是重来，是带证据重试（50 秒）

**操作**：选预设 B「P01 · 质检重试」，运行；展开 Trace 的第 6 步。

**讲解点**：
- 第一次 `qa.check` 返回 FAIL 64；执行器只重试失败步骤，`round=1`，不是整条重跑。
- 重试后 PASS 86；`promptDelta` 记录本轮补了什么约束。
- 事件数从 30 增到 36；成本 `¥0.2136`，重试成本单独可查。
- 最终仍然停在 `review`，不会自动发布。

**收句**：
> “失败路径有完整 trace，能复盘、能计价、能解释，这比‘一次成功’更像工程系统。”

## 4. 工作台 C：预算闸门 + 人工驳回（55 秒）

**操作**：选预设 C「P01 · 预算闸门」，运行；弹窗出现后点「驳回」。

**讲解点**：
- 预算 ¥0.10，跑到第 5 步已花 ¥0.1084，触发 80% 闸门（实际 108%）。
- 驳回事件是 `hitl.reject`，状态迁移到 `failed`；step5 FAIL，step6/7 BLOCKED。
- 产物 0 件：闸门之前没有落物料；成本停在 ¥0.1084。
- 批准分支是 `hitl.approve → running → review`；两条分支都真实走回调，不写死结果。

**收句**：
> “Human-in-the-loop 不是弹个窗，是状态机里的一条真实分支。”

## 5. 评测：20 条任务与 Prompt 回归（60 秒）

**操作**：切到「评测」→ 点「跑全量 20 条」→ 等 `PASS 20/20` → 打开导出报告。

**讲解点**：
- 数据集 20 条，覆盖 p01–p20、四组渠道组合、固定 seed；单条预算 ¥0.2。
- baseline v1.1.0 严格主色阈值 37%：9/20 通过（45%）。
- candidate v1.2.0 阈值 35%：20/20 通过（100%）；+55pp，11 条修复，0 条回归。
- 同一批 artifacts 换 rubric 复算，不换生成结果，所以差异只来自规则版本。
- 失败样例可点开：例如 E-02 的 c08 主色 36.64%，在 v1.1 失败、v1.2 通过。
- 结果落 `evals` store，共 40 条（20 任务 × 2 版本）；报告可导出 JSON。

**收句**：
> “评测不是跑一次看运气，而是固定数据集、固定 seed、固定阈值，能重复对照。”

## 收尾（18 秒）

> “三句话总结：单源配置让 17 页和后台不打架；运行时让每次 AI 调用可追踪、可计价；闸门与评测让它可被管理。方案 B 会把这一层接到真实模型和真实发布链路，A 先把证据链做扎实。”

## 演示前检查

1. 用 Chrome / Edge 打开，地址栏确认 `file://`，不要用 `http://`。
2. `workbench.html` 顶部 provider 显示 `mock`；若为 `replay`，切回 `mock` 再跑 A/B/C。
3. 评测页先看「NOT RUN」空态；跑批后应为 `PASS 20/20`。
4. 若现场时间被压缩，优先保 1、2、4、5；第 3 步可只讲 Trace 截图。
5. 所有截图在 `docs/v3/evidence/S5_*.png`，报告在 `docs/v3/reports/S5*.json`。
6. 如果现场刚跑过评测 / 自检，P0 会跟随“最新生产 run”，ID 可能不是 `R-0034`；S4 报告里的 `R-0034` 是 07:54 的冻结快照，第 1 步以屏幕当前 ID 为准，数字口径不变（7/7 · 3 件 · ¥0.1168 · 850ms）。
